<H1>Designing Our Database: Raw and Staging Tables</H1>

<Paragraph>There's one important decision we need to make,</Paragraph>

<Highlight block>How should we organize our incoming and processed data inside MySQL?</Highlight>

<Paragraph>Rather than loading everything directly into a single set of tables, we'll maintain two separate layers</Paragraph>

<NumberList items={[
  "Raw Tables",
  "Staging Tables"
]}
/>

<Highlight block>But why do we need two sets of tables for the same datasets? Let's understand.</Highlight>

<H2>Raw Tables: Preserving Incoming Data</H2>

<Paragraph>Raw tables act as the initial storage layer for our incoming data.</Paragraph>

<Paragraph>When we extract records from our source files, we load them into the corresponding raw tables with minimal or no modifications.</Paragraph>

<Paragraph>The main idea is to preserve the original incoming information rather than immediately changing or cleaning it.</Paragraph>

<Paragraph>Think of raw tables as our starting point. They help us understand what actually came into our pipeline.</Paragraph>

<H2>Staging Tables: Preparing Data for Further Processing</H2>

<Paragraph>Once our data is available in raw tables, we move towards the transformation stage.</Paragraph>

<Paragraph>This is where staging tables come in.</Paragraph>

<Paragraph>For example, we might remove duplicate records, handle missing values, standardize text, or correct data types before loading the processed records into staging tables.</Paragraph>

<Paragraph>In simple terms, raw tables preserve what came in, while staging tables hold what we've prepared.</Paragraph>

  caption="Raw tables keep a faithful copy of the source; staging tables hold the cleaned, typed rows that are ready to use."

<H1>Stage 1: Extract</H1>

<Paragraph>Now that our database structure is ready, let's begin implementing the first stage of our ETL pipeline: <Highlight>Extraction</Highlight>.</Paragraph>

<Paragraph>Remember, extraction is simply about retrieving data from our source systems. In our project, the source is four CSV files.</Paragraph>

<Paragraph>We use Pandas to read each file into a DataFrame.</Paragraph>

<CodeSnippet
  filename='extract.py'
  lang='python'
  code={`from pathlib import Path

import pandas as pd

# PROJECT_ROOT is the main ecommerce_etl folder.
PROJECT_ROOT = Path(__file__).resolve().parents[1]

CSV_FILES = {
    "customers": "customers.csv",
    "products": "products.csv",
    "orders": "orders.csv",
    "order_items": "order_items.csv",
}

def extract_data():
    # raw_data is a dictionary
    # It will hold name of the file as a key and its dataframe as a value
    raw_data = {}

    for key, filename in CSV_FILES.items():
        raw_data[key] = pd.read_csv(PROJECT_ROOT / "data" / "raw" / filename)

    return raw_data
`}
/>

<Paragraph>The extracted data isn't necessarily ready to be used. We may encounter missing values, duplicate records, inconsistent formats, or incorrect data types.</Paragraph>

<Paragraph>That's why we need the next stage.</Paragraph>

<H1>Stage 2: Transform</H1>

<Paragraph>Now that we've extracted our data, it's time to prepare it.</Paragraph>

<Paragraph>Transformation is where we apply the necessary changes to make our data consistent, accurate, and suitable for further processing.</Paragraph>

<Highlight>Clean Customers Data</Highlight>

<CodeSnippet
  filename='transform.py'
  lang='python'
  code={`def transform_data(raw_data):
    customers = raw_data["customers"].copy()
    for column in ("customer_name", "city"):
        customers[column] = customers[column].str.strip()
    customers["email_missing"] = customers["email"].isna()

    if customers["customer_id"].duplicated().any():
        raise ValueError("Duplicate customer IDs found")
`}
/>

<Paragraph> We remove extra spaces from names and cities, flag customers with a missing email, and check that customer IDs are unique.</Paragraph>

<Highlight>Clean Orders Data</Highlight>

<CodeSnippet
  filename='transform.py'
  lang='python'
  code={`orders = raw_data["orders"].copy()

    # Convert date columns into Pandas datetime format.
    for column in ("order_date", "created_at", "updated_at"):
        orders[column] = pd.to_datetime(
            orders[column], format="mixed", dayfirst=True, errors="coerce"
        )
    # Remove extra spaces and standardize order status capitalization.
    orders["status"] = orders["status"].str.strip().str.title()

    # Check for duplicate order IDs.
    if orders["order_id"].duplicated().any():
        raise ValueError("Duplicate order IDs found")
    
    # Check for missing or invalid dates.
    for column in ("order_date", "created_at", "updated_at"):
        if orders[column].isna().any():
            raise ValueError("Invalid order dates found" if column == "order_date"
                             else f"Invalid {column} dates found")
        
    if not orders["customer_id"].isin(customers["customer_id"]).all():
        raise ValueError("Unknown customer IDs found in orders")
`}
/>

<Paragraph>We convert order_date, created_at, and updated_at to Pandas datetime for consistent handling, then validate by checking for duplicate order IDs, missing/invalid dates, and that every customer_id in orders exists in customers.</Paragraph>

<Highlight>Enriching Order Items</Highlight>

<Paragraph>The source CSV for order items only stores a product_id, no price and no line total. Those live elsewhere (price in products, quantity in order_items), so we'll joins them together and calculate a line total.</Paragraph>

<CodeSnippet
  filename='transform.py'
  lang='python'
  code={`items = raw_data["order_items"].copy()

items = items.merge(
    products[["product_id", "price"]],
    on="product_id",
    how="left"
)

items = items.rename(columns={"price": "unit_price"})

# line_total is a new numeric column: quantity * unit_price.
items["line_total"] = items["quantity"] * items["unit_price"]
`}
/>

<Paragraph>We enrich it by left-joining each row against the products table to bring in the unit price, renaming that column to unit_price and then computing line_total as quantity × unit_price.</Paragraph>

<Paragraph>We also check that every order belongs to a real customer, and that every order item points to a real order and product.</Paragraph>

<H1>Stage 2: Load</H1>

<Paragraph>Once the data has been extracted and transformed, the final step is to load it into our MySQL database.</Paragraph>

<Paragraph>In this part, We divide the loading process into <Highlight>Raw</Highlight> and <Highlight>Staging</Highlight> tables.</Paragraph>

<Paragraph>Let's break down how the loading process works.</Paragraph>

<H2>Insert or update, Never Duplicate</H2>

<Paragraph>We use an upsert instead of a plain insert. This means we insert new rows and update existing rows when the primary key already exists.</Paragraph>

<Paragraph>But first, what is UPSERT?</Paragraph>

<Paragraph>UPSERT combines two operations:</Paragraph>

<NumberList items={[
  "**INSERT**: If a record doesn't already exist, insert it",
  "**UPDATE**: If a record with the same primary key already exists, update its values."
]}
/>

<Paragraph>This is useful because running the pipeline multiple times shouldn't create duplicate records.</Paragraph>

<CodeSnippet
  filename='load.py'
  lang='python'
  code={`query = text(f"""
    INSERT INTO {table_name} ({column_names})
    VALUES ({placeholders})
    ON DUPLICATE KEY UPDATE
    {update_clause}
""")

connection.execute(
    query,
    records.to_dict("records")
)
`}
/>

<Paragraph>What's happening here?</Paragraph>

<BulletList items={[
  "INSERT INTO specifies the target table and columns where records should be inserted",
  "VALUES provides placeholders for the incoming records",
  "ON DUPLICATE KEY UPDATE updates an existing record if its primary or unique key already exists, instead of inserting a duplicate",
  "execute() sends the query and the DataFrame records to MySQL"
]}
/>

<Paragraph>For example, suppose customer 101 already exists in our database, but their city changes from Karachi to Lahore.</Paragraph>

<Paragraph>Instead of inserting another customer record, UPSERT updates the existing record.</Paragraph>

<H2>Loading Customers Data</H2>

<Paragraph>With our reusable function ready, we can load customers into its respective raw and staging tables.</Paragraph>

<CodeSnippet

        upsert_dataframe(

<Paragraph>What's happening here?</Paragraph>

<BulletList items={[
  "First, customer records are loaded into raw_customers, using the original source columns",
  "Next, the same records are loaded into staging_customers, including the additional email_missing column created during transformation"
]}
/>

<Paragraph>We follow the same approach for other tables, adjusting the column lists according to their respective transformations.</Paragraph>

<H2>Incremental Loading of Orders</H2>

<Paragraph>We'll implement incremental loading for the orders dataset.</Paragraph>

<Paragraph>Why?</Paragraph>

<Paragraph>Imagine having a database with thousands of orders. Every time the pipeline runs, loading all historical orders again would be unnecessary.</Paragraph>

<Paragraph>Instead, we only want to load Newly created orders and existing orders that have been modified since the previous pipeline run.</Paragraph>

<Paragraph>To achieve this, I used a concept called <Highlight>Watermarking</Highlight>.</Paragraph>

<H3>What is a Watermark?</H3>

<Paragraph>A watermark is a reference point that tracks how far a data pipeline has processed its source data.</Paragraph>

<Paragraph>In this project, we use the updated_at column to identify new or modified orders.</Paragraph>

<Paragraph>For this, lets create a watermark table:</Paragraph>

<CodeSnippet
  filename='load.py'
  code={`CREATE TABLE IF NOT EXISTS etl_watermarks (
    pipeline_name VARCHAR(100) PRIMARY KEY,
    last_watermark DATETIME NOT NULL)
`}
/>

<Paragraph>This table stores the last successfully processed timestamp for each pipeline.</Paragraph>

<Paragraph>Before loading orders, the pipeline retrieves the previous watermark</Paragraph>

<CodeSnippet
  filename='load.py'
  lang='python'
  code={`last_watermark = get_watermark(connection)
`}
/>

<Paragraph>Then, it filters the incoming orders</Paragraph>

<CodeSnippet
  filename='load.py'
  lang='python'
  code={`incremental_orders = orders[
    orders["updated_at"] >= pd.Timestamp(last_watermark)
].copy()
`}
/>

<Paragraph>This selects only records whose updated_at timestamp is later than the previous watermark.</Paragraph>

<Paragraph>For example, suppose our previous watermark is 2026-11-10 12:00:00.</Paragraph>

<Table
  headers={['order_id', 'updated_at', 'action']}
  rows={[
    ['501', '2026-11-09, 10:00 AM', 'Skip'],
    ['502', '2026-11-11, 11:00 PM', 'Load'],
    ['503', '2026-11-08, 08:00 AM', 'Skip'],
    ['504', '2026-11-12, 12:00 PM', 'Load']
  ]}
/>

<Paragraph>Only orders 502 and 506 are selected for loading.</Paragraph>

<Paragraph>After successfully loading the selected orders into both raw and staging tables, we update the watermark</Paragraph>

<CodeSnippet
  filename='load.py'
  lang='python'
  code={`new_watermark = incremental_orders["updated_at"].max()

connection.execute(
    text("""
        UPDATE etl_watermarks
        SET last_watermark = :new_watermark
        WHERE pipeline_name = 'orders'
    """),
    {"new_watermark": new_watermark.to_pydatetime()}
)
`}
/>

<Paragraph>Here, we find the latest updated_at timestamp among the successfully processed records and save it as the new watermark.</Paragraph>

<Paragraph>This ensures that the next pipeline execution starts from the latest processed point rather than loading the same records again.</Paragraph>

<H2>Handling Deleted Records</H2>

<Paragraph>Another important consideration in an ETL pipeline is handling deleted records.</Paragraph>

<Paragraph>For example, suppose a customer is removed from our source CSV. A normal UPSERT won't detect this deletion because it only inserts or updates records.</Paragraph>

<Paragraph>To handle this, we implement <Highlight>soft deletion</Highlight>. Instead of physically deleting records from the database, we use an is_deleted column to track their status.</Paragraph>

<BulletList items={[
  "**FALSE**: The record is active",
  "**TRUE**: The record has been marked as deleted"
]}
/>
<Paragraph>First, we create a temporary table to store the IDs currently available in our source dataset.</Paragraph>

<CodeSnippet
  filename='load.py'
  lang='python'
  code={`
CREATE TEMPORARY TABLE current_keys (
    key_value INT NOT NULL PRIMARY KEY
);

`}
/>

<Paragraph>We then insert the source IDs into this temporary table</Paragraph>

<CodeSnippet
  filename='load.py'
  lang='python'
  code={`
keys = dataframe[[key_column]].drop_duplicates()

connection.execute(
    text("""
        INSERT INTO current_keys (key_value)
        VALUES (:key_value)
    """),
    [
        {"key_value": int(value)}
        for value in keys[key_column].tolist()
    ]
)`}
/>

<Paragraph>Now, we compare these IDs with the records already stored in MySQL. Any database record that is missing from the source snapshot is marked as deleted.</Paragraph>


<CodeSnippet
  filename='load.py'
  lang='python'
  code={`
UPDATE raw_customers AS t
LEFT JOIN current_keys AS c
    ON t.customer_id = c.key_value
SET t.is_deleted = TRUE
WHERE c.key_value IS NULL
  AND (t.is_deleted = FALSE OR t.is_deleted IS NULL);
`}
/>

<Paragraph>The same operation is performed on the staging table.</Paragraph>

<Paragraph>This approach preserves historical records and maintains relationships between tables. For example, an old order can still reference a customer who has been marked as deleted.</Paragraph>

<Paragraph>And this is how, we've successfully built our first ETL pipeline using Python and MySQL!</Paragraph>
